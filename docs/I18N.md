# Languages: how the wiki is translated and how to keep it up to date

The wiki text in the code and data stays English. Each language (vi, ru, pt-BR, es) is a **pack**: a table from the hash of an English sentence to its translation, built into the site (`static/lang-<l>.js`, inline in the offline file). A sentence without an entry shows its English, so nothing breaks when the data grows; the checks tell you what is missing.
Plan and history: `docs/plans/2026-11-08-multilingual.md` (§13 is the log) and `docs/plans/2026-11-11-i18n-quality-and-structure.md`.

## Where things live
| What | Where |
|---|---|
| Interface texts of the page shell (`data-i18n` keys, `ui.json`) | `build/i18n/ui.json` |
| Sentences the code writes: `T("…")`, `TN(n,"one","other")` | in `app.js`, `gear.js`, `ux.js`, `rooms.js`; their translations are in `build/i18n/tm/<lang>/ui.json` |
| Data text (curio effect lines, source lines, tooltip lines, bosses, guide book, gear attribute names, relic panel) | read at run time through `TD(english)`; translations in `tm/<lang>/{fx,src,st,boss,guide,gear,relic,vocab,names}.json` |
| The game's and mods' own translations | `build/i18n/official/<lang>.json` (made by `harvest.py`; a sentence of ours wins over them) |
| Words that are never translated (proper nouns) and the chosen terms | `build/i18n/keep.json`, `build/i18n/glossary.json` |
| Checks | `build/checks/i18n.js` (run by `check.sh`); `build/i18n/tools/qa.py` (typography, symbols, glossary, English left over) and `tools/terms.py` (does a word read as the game says it?) check the translation text itself |
| Minecraft's own words in the four languages | `build/i18n/official/vanilla_terms.json` (made by `tools/vanilla_terms.py`): the reference for effect, attribute, mob and item words |
| Tools | `build/i18n/tools/`: `status.sh`, `todo.js`, `merge.py`, `review.py` (spreadsheet out and back for native reviewers), `qa.py`, `terms.py`, `align_terms.py`, `inv.js`, `identity.sh`, `leftover.js`, `domains.js` |

A translation entry: `"<hash>": {"en": "<English>", "t": "<text>", "s": "llm|official|human"}`; `t` is an object of plural forms (`one`, `few`, `many`, `other`) for `TN` sentences, whose English is `<one>␁<other>`. `s` says who made it: `llm` = machine translation awaiting a person, `human` = a person checked it. `r: "needs-review"` marks an entry to look at again.
Decimal signs: vi keeps the dot; ru, pt, es use the comma (` %` with a space in es). Numbers, `{placeholders}` and HTML tags must stay as in the English (`merge.py` and `build.py` check).

## When the pack (mods) or the English text changes: the loop
Run from the repo root; `NODE_PATH=$(npm root -g)` once for the Playwright tools.
1. `bash build/i18n/tools/identity.sh --save /tmp/base` (before you edit: remembers the English pages).
2. Change sources, `bash build/patches/apply_all.sh`.
3. `bash build/i18n/tools/status.sh` prints, per language and domain, entries by state, strings still **without a translation** (`todo.json` in `/tmp/i18n-status` has the lists) and **orphans** (entries whose English is gone).
4. Translate the missing strings in batches of about 100: write `idx|vi|ru|pt|es` lines against a JSON list of the English, then `python3 build/i18n/tools/merge.py --domain fx list.json batch.txt` (add `--dry` first). Sentence shapes the engines compose (source lines `srcT`, attribute lines `gAL`, config lines) need a clause or a name in the table, not every combination.
5. `node build/i18n/tools/inv.js` (15 s) runs the i18n invariants; `python3 build/i18n/tools/qa.py` checks typography and the glossary; `python3 build/i18n/tools/terms.py --lang ru` lists game words the wiki says differently from the game.
6. `bash build/i18n/tools/identity.sh /tmp/base` must print `English identical`.
7. Look at a page of each language you touched (`node build/shot.js '#i5' --lang ru`), then the full `bash build/check.sh`, one commit with a NOTES entry.

## Adding one string by hand
Write it in the code as `T("English {x}", {x})` or add the English to the data, run the build: `build.py` stops and names every `T()` sentence that has no entry (`… untranslated: …`). Add the four translations with `merge.py --pairs` (a JSON `{english: [vi, ru, pt, es]}`).

## Reviewing as a native speaker
The easy way, for someone who is not a developer: `python3 build/i18n/tools/review.py export ru --domain ui,vocab --out ru.csv` writes a spreadsheet (UTF-8 CSV, opens in Excel or Google Sheets) with one row per entry not yet checked: id, domain, state, english, translation, ok, comment. The reviewer fixes the `translation` column, writes `x` in `ok` on a row that is right as it is, and may leave a comment. `review.py import ru ru.csv --dry` then shows what would change; without `--dry` it writes the TM: a changed row is checked like `merge.py` checks it (same digits, `{placeholders}` and tags as the English; a row that fails is listed and skipped) and becomes `"s": "human"`, a confirmed row becomes `human`. The domains in the order a reader meets them: ui, vocab, gear, relic, st, cfg, fx, src, guide, boss, names; start with `ui,vocab`. After an import run `apply_all.sh`, `node build/i18n/tools/inv.js` and `python3 build/i18n/tools/qa.py --strict`.

The direct way: open the domain file of your language (`build/i18n/tm/<lang>/<domain>.json`), read `en` and `t`, fix `t` and set `"s": "human"` on what you checked.

## Names and proper nouns
Proper nouns are never translated: the pack's and the mods' own names, bosses, characters, Acts with a name (`Warden Act`). Everything else is translated. An item with a common-noun name is translated, unless the game's own translation exists, which wins. The page always shows the English name next to a translated name and the search finds both: `enAlt(name)` is the small muted line under the page title (curio, gear, set pages) and `enTip(name)` the same line in the tooltip; both are empty in English and for a name left English.

How a name is written (the names in `tm/<lang>/names.json`): vi Title Case, ru and es sentence case, pt Title Case. Materials say what the game says (`official/vanilla_terms.json`: vi Netherite, ru незеритовый, pt Netherita, es netherita; Glowstone, Obsidian, Redstone by the same table); a metal a mod coined keeps its English spelling in vi/pt/es and is spelled in Cyrillic in ru (ru "из пласлитерита"). A level suffix `(Lv 3)` reads `(Cấp 3)`, `(ур. 3)`, `(Nv 3)`, `(niv. 3)`. A name that is only a proper noun, an acronym (BAFS, PDA) or a coined word is kept with `=` in the batch file. Look up how an earlier name was written before you write a new one (`grep` the TM file: "Diamond X" and "Iron X" are the model for every weapon type).

## Mods' own translations are sometimes old
A mod's `ru_ru.json` can be older than its `en_us.json`, so the Russian text under a key is the text of another version ("+0.1% Attack Speed" => "+10% Knockback Resistance"). `build.py` therefore does not use an official text whose numbers or placeholders differ from the English, or that is another English string of the file; it prints how many it left out per language. Names come from the id, so they are not affected.
