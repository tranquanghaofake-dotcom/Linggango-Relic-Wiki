# Linggango Relic Wiki: working rules

A static fan wiki for the Linggango modpack. Python builds it from data files; GitHub Actions checks it and deploys it to
https://tranquanghaofake-dotcom.github.io/Linggango-Relic-Wiki/ (offline single file: `/dist/Linggango_Relic_Wiki.html`).
The wiki text stays in English; the user reads Vietnamese, so talk to them in Vietnamese.

## How a change goes live
1. Edit sources only (next section).
2. `bash build/patches/apply_all.sh` (about 10 s) — the whole build: data patches, `build.py`, curio tiers. Never `build.py` alone: it skips the curio tiers, which move when scoring in `gear.js` changes.
3. Look at every page you changed: `node build/shot.js '#home' '#g12' …` (add `--width 375` for phones), then open the PNGs. A change nobody has looked at is not done. A change that should leave pages as they were: shoot the previous build too and add `--diff <its shot dir>`.
4. `bash build/check.sh` (about 5 min) — exactly what CI runs before deploying.
5. One commit: the sources plus this session's entry in `docs/NOTES.md`. Push to `main`.
6. The `site` workflow (`.github/workflows/site.yml`) builds, checks and deploys. A red run deploys nothing and the site stays on the last good build; `/build.txt` on the site names the deployed commit. Check the run went green before saying the change is live.

## What to edit
| Edit | Never edit by hand |
|---|---|
| `build/src/app.js`, `gear.js`, `ux.js`, `rooms.js`, `template.html`, `v5.css`; `build/style.game.css` | `index.html`, `static/`, `dist/` — build outputs, git-ignored |
| `build/patches/*.json` and `*.py` (facts and the rules that combine them) | `build/src/gear_data.js`, `build/src/wiki_data.js` — generated by `apply_all.sh`, git-ignored |
| `build/src/data.js` — curios, hand-maintained; `boss_stats.py`/`boss_order.py` also write into it, so commit what the build changes | `build/patches/boss_portraits.json` — `node build/pack_audit/boss_portraits.js` from `boss_models.json` |
| | `build/src/scenes.js`, `build/src/uiicons.js` — regenerate with their `pack_audit/` scripts |

How the pieces fit: `build/README.md`; why they are shaped that way: `build/ARCHITECTURE.md`.

## Branches and files
- `main`: sources, build scripts, docs and notes. Pages serves only the workflow's artifact, never the branch itself.
- `workspace`: orphan archive — the asset library (`assets/`, read by `pack_audit/uiicons.py`), `build/migrations/`, old prompts and screenshots. Never merge it; take one file with `git checkout origin/workspace -- <path>`.
- No other branches and no pull requests unless the user asks.
- One file per thing: update it in place. No `_v2`/`_final`/`_new` copies, no duplicate pages or scripts; git history keeps the old versions.

## Notes
`docs/NOTES.md` is the project log. Append one entry per session at the end: `## YYYY-MM-DD: <what changed>`, then what was done, what was checked and how, and what is still open (with the reason). Keep "still open" items until they are done or the user drops them.

## Skills and agents
- Which third-party skills this repo uses, where each lives and what was left out: `docs/AGENT_TOOLS.md`. These rules win over any skill.
- Anything beyond one page or one tool starts with a plan: superpowers `brainstorming` → short design doc → `writing-plans`, saved as `docs/plans/YYYY-MM-DD-<topic>.md`; then `executing-plans` or `subagent-driven-development`. A session the user is not watching lays the approaches out in its reply and goes on with the one it recommends; a change to the look still waits for approval.
- Code changes follow `.claude/skills/ponytail`: the smallest change that fully solves the task, callers and checks included; `ultra` when folding tools together.
- "Done" means steps 3–4 above ran in this session (superpowers `verification-before-completion`).
- Account plugins (claude.ai → Customize → Plugins) reach cloud sessions and the owner's machine; `~/.claude/agents` on a machine reaches that machine only. Skills that would change the look (UI UX Pro Max, Impeccable) or the reply style (Caveman) are not used.

## Facts
- Numbers come from the game export first, then the pack's files, then the jar reading. External wikis are reference only. Estimates are labelled as estimates.
- Every bug found in the data becomes an invariant in `build/check.js`.
- Textures follow the licence rules in `build/README.md` (Rooms): nothing All Rights Reserved or NoDerivatives.

## Design
- The look is Minecraft's own GUI: bevelled containers, stone buttons, inset item slots, the vanilla tooltip, advancement frames, the boss bar, and the motion that goes with them. It is deliberate; keep it.
- Do not flatten or strip it. A pass that removed the bevels, shadows and animations was reverted at the user's request (it read as plain, not clean). Any change to the overall look needs the user's approval first.
- Do not build what the reader cannot see yet: The Path opens one Act (the reader's "I'm here" Act, else Act 0–I) and builds a collapsed Act's tiles when it opens.
- Desktop and laptop first; check phones (375 px) for anything that can overflow.

## Content
- Naming: the progression as a whole is "The Path"; each stage is an "Act" (Act 0–I, Act II, … Warden Act).
- The curio list page (`#home`) is called "Curios" (nav, breadcrumbs, title); "The Path" names the progression map on the hub and the Acts, not that page.
