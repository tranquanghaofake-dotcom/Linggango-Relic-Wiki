# Linggango Relic Wiki: working rules

A static fan wiki for the Linggango modpack. Python builds it from data files; GitHub Actions checks it and deploys it to
https://tranquanghaofake-dotcom.github.io/Linggango-Relic-Wiki/ (offline single file: `/dist/Linggango_Relic_Wiki.html`).
The wiki text stays in English; the user reads Vietnamese, so talk to them in Vietnamese.

## How a change goes live
1. Edit sources only (next section).
2. `bash build/patches/apply_all.sh` (about 10 s) — the whole build: data patches, `build.py`, curio tiers. Never `build.py` alone: it skips the curio tiers, which move when scoring in `gear.js` changes.
3. Look at every page you changed: `node build/shot.js '#home' '#g12' …` (add `--width 375` for phones), then open the PNGs. A change nobody has looked at is not done. A change that should leave pages as they were: shoot the previous build too and add `--diff <its shot dir>`.
4. `bash build/check.sh` (about 6 min) — exactly what CI runs before deploying.
5. One commit: the sources plus this session's entry in `docs/NOTES.md`. Push to `main`.
6. The `site` workflow (`.github/workflows/site.yml`) builds, checks and deploys. A red run deploys nothing and the site stays on the last good build; `/build.txt` on the site names the deployed commit. Check the run went green before saying the change is live. A commit that only touches Markdown, `docs/` or `.claude/` starts no run (`paths-ignore`): the site keeps its build, and `/build.txt` names the last commit that changed it.

How the pieces fit: `build/README.md`; why they are shaped that way: `build/ARCHITECTURE.md`.

## Branches and files
- `main`: sources, build scripts, docs and notes. Pages serves only the workflow's artifact, never the branch itself.
- `workspace`: orphan archive — the asset library (`assets/`, read by `pack_audit/uiicons.py`), `build/migrations/`, old prompts and screenshots. Never merge it; take one file with `git checkout origin/workspace -- <path>`.
- No other branches and no pull requests unless the user asks.
- One file per thing: update it in place. No `_v2`/`_final`/`_new` copies, no duplicate pages or scripts; git history keeps the old versions.

## Notes
`docs/NOTES.md` is the project log. Append one entry per session at the end: `## YYYY-MM-DD: <what changed>`, then what was done, what was checked and how, and what is still open (with the reason). Keep "still open" items until they are done or the user drops them.

## Process (what happens around steps 1–6)
- **Classify first** (superpowers `brainstorming`): a spike (an answer, nothing kept), a bounded change (one page or one tool of the site or build, a doc, a process rule: say the approach in a sentence, then steps 1–6), or architectural (a new area, several tools, a change to how things fit). Only architectural work gets a written plan, `docs/plans/YYYY-MM-DD-<topic>.md`, spec and plan in one file when the plan is short; then `executing-plans` or `subagent-driven-development`. A session the user is not watching lays the approaches out in its reply and goes on with the one it recommends; a change to the look still waits for approval.
- **Facts before code** (Facts section). Pages read through the Firecrawl or Parallel connectors are reference, never numbers.
- **Smallest complete change:** `.claude/skills/ponytail`, callers and checks included; `ultra` when folding tools together.
- **Bugs:** superpowers `systematic-debugging`; the fix ends as an invariant in `build/checks/<topic>.js` (loaded by `check.js`). Linters are hand tools here, not gates (`docs/AGENT_TOOLS.md`).
- **Done means evidence:** steps 3–4 ran in this session (superpowers `verification-before-completion`); "live" means the `site` run went green, read with the GitHub connector (`actions_list` on this repo) or on the Actions page.
- **Review before merge** for architectural work: `requesting-code-review` or `/code-review` on the branch, before `main`.
- **Value first:** before work that takes more than about an hour, say in one line what a reader of the wiki will see change. Tool refactors whose only proof is "the output stays byte-identical" wait until a reader-visible fix needs them (the classlib chunks 1B/1C cost hours for nothing on the pages and were dropped). When the visible gain is small, ask the owner before starting.
- **Who does it:** a task under about 30 minutes is done directly, without an agent. An agent's brief asks for the proof the change needs, not more; a stopped agent (usage limit) is resumed, not restarted. Integrate agent work the same day, then delete its worktree and branch.
- **Checks during work:** `node build/check.js` (about 5 min) while working; `bash build/check.sh` once per wave, before pushing to `main`.
- **Docs say only what was checked:** before writing "done", "retired", "stale" or a count into a doc or NOTES, verify it (grep, run, count). A claim found wrong later is corrected in NOTES in the open.
- **Big passes (audits, many fixes):** high-severity first, then ship (steps 2–6) before medium and low; low ones may wait for another session. One finding belongs to one group of files, never split in halves; each group adds its own invariant file and gets one review at the end, not one per chunk.
- **Budget:** the account has a five-hour usage limit. Fable (max) only for planning and rating; Sonnet for simple fixes and for verifying low/medium findings; Opus for complex ones. At most two heavy agents at once and at most two parallel builds (the machine has 4 CPUs; more makes `check.js` 10x slower). Estimate the tokens of a workflow before launching it; a workflow script runs once with a dry-run flag (no agents) before it runs for real.
- **Generated files:** commit what `apply_all.sh` rewrites (`data.js`, `curio_tiers.json`) in the same commit as the change that caused it; a conflict in them is solved by taking either side and running `apply_all.sh`.
- Which skills, connectors and open-source tools this repo uses, where each lives and what was left out: `docs/AGENT_TOOLS.md`. These rules win over any skill. Account plugins reach cloud sessions and the owner's machine; `~/.claude/agents` on a machine reaches that machine only.

## Facts
- Numbers come from the game export first, then the pack's files, then the jar reading. External wikis are reference only. Estimates are labelled as estimates.
- Every bug found in the data becomes an invariant in `build/checks/<topic>.js`.
- Textures follow the licence rules in `build/README.md` (Rooms): nothing All Rights Reserved or NoDerivatives.

## Design
- The look is Minecraft's own GUI: bevelled containers, stone buttons, inset item slots, the vanilla tooltip, advancement frames, the boss bar, and the motion that goes with them. It is deliberate; keep it.
- Do not flatten or strip it. A pass that removed the bevels, shadows and animations was reverted at the user's request (it read as plain, not clean). Any change to the overall look needs the user's approval first.
- The home page opens on The Path at dusk ("The climb": a sunset sky and a staircase of blocks, one step per Act, its Keeper on top playing its idle loop and walking when pointed at, a sky that moves: clouds, sun rays, birds, wind; below it the cave wall whose ores twinkle now and then, and the shelves as trays of slots in the wiki's own dark panels), the direction the user chose on 2026-11-11. The other main pages do not copy that sky: each keeps its own room, and the room's wall spreads behind the whole page (`rooms.js rWall`). Further phases are shown to the user first (`docs/plans/2026-11-11-the-climb.md`).
- Do not build what the reader cannot see yet: The Path opens one Act (the reader's "I'm here" Act, else Act 0–I) and builds a collapsed Act's tiles when it opens.
- Desktop and laptop first; check phones (375 px) for anything that can overflow.

## Content
- Naming: the progression as a whole is "The Path"; each stage is an "Act" (Act 0–I, Act II, … Warden Act).
- The curio list page (`#home`) is called "Curios" (nav, breadcrumbs, title); "The Path" names the progression map on the hub and the Acts, not that page.
